# Добавление замка

Применять к этому компоненту. Сначала прочитать [ARCHITECTURE.md](../../ARCHITECTURE.md), `models/a1_ultra.py`, `registry.py` и относящиеся к изменению команды/тесты внутри `custom_components/tuya_local_ble_custom/`. Секреты и эксплуатационные сведения конкретной установки в репозиторий не добавлять.

## Выбрать минимальное расширение

- Установить точные product_id, category, сервис Bluetooth, способ авторизации и доказанные команды. Название продавца и совпадение категории не доказывают совместимость.
- Если отличается только идентификатор при одинаковом обмене данными: отдельный файл в `models/`, наследник `A1UltraModel`, переопределить `product_id` и `name`, при необходимости подтверждённую `category`. Остальные команды, протокол, поля настройки и возможности наследуются. Пример есть в ARCHITECTURE.md.
- Если совпадает большая часть модели: наследник может заменить один объект команды или декодер после `super().__init__`. Проверить обе стороны: запись нового DP и чтение/отображение ответа. Не копировать весь класс ради одной команды.
- Если общим остаётся лишь протокол: собственный `LockModel` с композицией переиспользуемых команд. Не строить ложное наследование от A1 и не оставлять чужие функции включёнными.
- Новый формат команды разместить отдельным классом в `protocols/<protocol>/commands/`; новый формат ответа — в `dialects/`. Самостоятельный протокол связи — отдельный пакет `protocols/`, реализующий контракт сессии. Транспорт, кодек, модель и сущности HA имеют разные обязанности.

## Регистрация и настройка

Единственная точка регистрации модели — `registry.py`: импорт класса и `register_model(Class)`. Идентификатор задаётся один раз на классе; не размножать его в flow, keyman, platform-файлах и протоколе. Дубликат product_id должен завершаться ошибкой, а не молча заменять модель.

Из класса берутся `protocol_id`, `credential_fields`, `validate_credentials` и `capabilities`. Поля формы не должны содержать реальные ключи или автоматически подставлять чужие данные. При новом поле добавить подписи переводов. Совместимая модель с существующими полями/функциями не требует правок HA-адаптеров.

Новый протокол регистрируется рядом с остальными. Для нового UUID обновить также статическое Bluetooth-объявление manifest: это обязательное требование HA, не дополнительная регистрация каждой модели. Новая пользовательская функция вне существующих capabilities требует своего HA-адаптера и переводов; не выдавать её за уже поддержанную.

## Проверить поведение

- Проверить выбор модели по ID/категории, создание сессии через реестр и наследование без правок ядра. Использовать искусственную вторую модель в тестах; не добавлять её в каталог поддерживаемых устройств.
- Проверить точные пакеты на синтетических данных, обратный разбор состояния, неизвестные/повреждённые ответы, неверные значения и отсутствие успеха после тайм-аута.
- Убедиться, что setup/heartbeat не запускают мотор и что после ошибки команда открытия/закрытия/калибровки не повторяется автоматически.
- Запустить относящиеся unit-тесты, проверки реальных HA-адаптеров и hassfest. Сохранить стабильность domain/unique_id для существующих записей.
- На реальном замке проверять только разрешённые владельцем действия. Подтверждение BLE-пакета не равно физическому успеху; отдельно фиксировать выполненные и непроверенные сценарии.

Обновить README со списком фактически проверенных моделей и INSTALL при изменении настройки. В PR описать совместимость, повторно использованные части, отличия и проверки. Не обещать поддержку только по совпадению category. Проверить отсутствие секретов и сохранность обязательных лицензионных уведомлений перед commit/push.
